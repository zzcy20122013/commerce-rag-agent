# 项目路演标准测试路径

这份文档只给我们自己做项目路演、录屏和现场自测用，不放进 README，也不作为对外公开说明。它的作用是把“最稳、最能体现项目价值”的操作路径固定下来，避免现场临时乱点。

路演优先用 Android 原生端展示；Web Debug 只作为备用调试界面，用来看 SSE、trace、商品卡片、图片上传和接口返回。

本轮主打加分项是 **4.3 对话智能与 RAG 增强**。现场讲解不要平均铺开所有能力，而是围绕“多轮约束继承 -> 反选排除 -> RAG 依据 -> 商品对比决策”这条深度链路展开；购物车、拍照和语音作为辅助展示即可。

## 0. 路演前准备

| 检查项 | 操作 | 通过标准 |
|---|---|---|
| 后端服务 | 仓库根目录运行 `.\scripts\start_backend.cmd` | `http://127.0.0.1:8000/health` 返回 `ok` |
| Android 端 | Android Studio 打开 `android/`，启动模拟器运行 App | 首页显示 `Commerce AI`，能发送消息 |
| 后端地址 | 模拟器访问后端使用 `http://10.0.2.2:8000` | 不再出现连接失败 |
| 会话状态 | 建议新开一个会话 | 避免上一次购物车、订单、记忆影响本次演示 |
| 模型状态 | 确认 `backend/.env` 中 Doubao Key 可用，且 `DOUBAO_MODEL` 可用于文本和视觉输入 | 大模型可用时回答和拍照识别更自然，不可用时 fallback 仍能跑 |
| 购物车/订单 | 开场前可以先清空购物车，必要时删除旧订单记录 | 现场路径更干净 |

如果后端临时不可用，Android 会走本地 Mock 兜底，可以展示聊天、商品卡、详情页和基本交互；但真实 RAG、SSE、购物车落库、订单、反馈和库存同步都要以后端在线模式为准。

## 1. 基础文本导购

| 项目 | 内容 |
|---|---|
| 演示目标 | 证明系统能从一句自然语言购物需求进入导购推荐链路 |
| 用户输入 | `推荐 3500 以内学生记笔记平板` |
| 期望现象 | 逐字流式回复；有主推和备选；展示商品卡片 |
| 重点观察 | 回答要像导购，不要像检索报告；商品卡片应有价格、销量、推荐理由 |
| 能力点 | IntentRouter、SQLite 结构化过滤、Chroma 召回/rerank、Doubao 生成、ResponseComposer、SSE、商品卡片 |
| 现场说法 | 用户只说预算、身份和用途，系统会自动识别品类、预算、用途，再把候选商品组织成导购建议。 |

备用输入：

- `推荐 300 以内通勤鞋`
- `找 100 元以内控油粉饼`
- `推荐适合敏感肌的防晒`
- `找低脂早餐麦片`
- `推荐通勤降噪耳机`

## 2. 多轮约束继承

| 项目 | 内容 |
|---|---|
| 演示目标 | 证明 Agent 能记住上一轮约束，不是每轮重新开始，这是 4.3 主线的第一步 |
| 第一步输入 | `推荐 300 以内通勤鞋` |
| 第二步输入 | `要轻便一点的` |
| 第三步输入 | `如果我更看重耐穿呢` |
| 第四步输入 | `不要刚才那个品牌` |
| 期望现象 | 后续仍围绕“300 以内 + 通勤鞋”，并追加轻便、耐穿偏好；反选时避开上一轮主推品牌 |
| 重点观察 | 不要跑偏到平板、护肤品；不要把“不要刚才那个品牌”当闲聊；trace 里应能看到有效约束、memory 快照和 guide_quality |
| 能力点 | 会话 memory、多轮约束继承、偏好追加、指代式品牌排除、类目 SOP、trace 可解释性 |
| 现场说法 | 真实导购不是单轮问答，用户会不断补条件，系统要能继承上下文。 |

## 3. 主推、备选和无严格匹配

| 项目 | 内容 |
|---|---|
| 演示目标 | 证明推荐有取舍，也能诚实处理不满足条件的情况 |
| 主推输入 | `推荐 3500 以内学生记笔记平板` |
| 无匹配输入 | `100 以内要 Nike 跑鞋` |
| 期望现象 | 有严格匹配时明确主推；没有严格匹配时说明“当前没有完全符合”，给放宽预算或换品牌建议 |
| 重点观察 | 不能把超预算商品说成预算内；不要平均介绍所有商品 |
| 能力点 | no_exact_match、预算约束、主推/备选/劝退话术、可信导购表达 |
| 现场说法 | 导购不应该只会硬卖，也应该告诉用户哪些条件下不建议强推。 |

## 4. RAG 推荐依据和评价风险

| 项目 | 内容 |
|---|---|
| 演示目标 | 证明推荐不是大模型凭空编，而是能解释依据和风险 |
| 用户输入 | `推荐适合敏感肌的防晒` |
| 期望现象 | 商品卡片显示简短推荐依据；如果评价里有刺痛、泛红等风险，要有温和提醒 |
| 重点观察 | 给用户看的文案要是“适合日常防晒、肤感轻薄、敏感肌先试用”这类人话，不要暴露“商品库结构化字段”等内部词；风险提示统一显示为温和的“评价提醒” |
| 能力点 | 商品详情 chunk、FAQ chunk、评论摘要、差评风险关键词、评价正负面洞察、卡片 evidence/source_summary |
| 现场说法 | 我们把商品描述、规格、FAQ、用户评价拆成不同知识块，推荐时能引用这些依据，也能提醒差评风险。 |

如果回答里出现明显内部词，比如“商品库结构化字段”，现场不要优先展示这条，后续再修话术。

## 5. 商品对比

| 项目 | 内容 |
|---|---|
| 演示目标 | 证明系统能基于上一轮推荐做对比，而不是重新乱搜，这是 4.3 主线的决策收口 |
| 第一步输入 | `推荐 3500 以内学生记笔记平板` |
| 第二步输入 | `它们两个区别是什么` |
| 期望现象 | 围绕上一轮前两个商品，从价格、用途、规格、评价等角度对比，并给一个选择建议 |
| 重点观察 | 回答要说“谁更适合什么场景”，不要只重复商品名 |
| 能力点 | Compare Agent、多轮 last_product_ids、商品结构化信息复用、ResponseComposer |
| 现场说法 | 用户真实决策经常发生在“推荐之后追问区别”，这条路径验证多轮和对比 Agent。 |

备用追问：

- `如果我更看重记笔记呢`
- `如果我更看重屏幕呢`
- `哪个更适合学生`

## 6. 自然语言购物车闭环

| 项目 | 内容 |
|---|---|
| 演示目标 | 证明系统不只是回答，还能执行轻量电商动作 |
| 前置步骤 | 先完成一次推荐，确保页面里有商品卡片 |
| 第一步输入 | `把前两个都加入购物车` |
| 第二步输入 | `查看购物车` |
| 第三步输入 | `第二个数量改成 10` |
| 第四步输入 | `清空购物车` |
| 期望现象 | 加购、查看、改数量、清空都实际生效；顶部购物车角标同步 |
| 重点观察 | “清空购物车”不能误判成加购；“第二个数量改成 10”要改购物车第二项 |
| 能力点 | PurchaseHelp Agent、Cart API、SQLite 落库、自然语言动作解析、Android 状态同步 |
| 现场说法 | 这里体现 Agent 从“给建议”向“帮用户操作”延伸。 |

备用输入：

- `把小米加入购物车`
- `这个加 3 件`
- `把防晒那个改成 2 瓶`
- `刚才第二个不要了`

如果自然语言解析现场不稳，可以改成点商品卡片上的“加入购物车”，再展示购物车查看、数量修改和删除。

## 7. 商品卡片、详情页和直接购买

| 项目 | 内容 |
|---|---|
| 演示目标 | 证明 Android 端不是静态聊天页，而是有商品详情和购买入口 |
| 操作步骤 | 点击商品卡片进入详情页；在详情页加购；返回聊天查看购物车角标 |
| 期望现象 | 详情页展示商品图、标题、价格、描述和购买入口；加购后角标同步 |
| 重点观察 | 详情页与聊天商品卡是同一套后端商品数据 |
| 能力点 | Android Compose、Product API、商品详情页、购物车状态同步 |
| 现场说法 | 从聊天推荐到详情页，再到加购/购买，是移动端导购产品的基本闭环。 |

如果需要展示“立即购买”，更自然的说法是：购物车里点“提交订单”，订单页再走支付、发货、收货、退款模拟流程。

## 8. 订单、售后和库存同步

| 项目 | 内容 |
|---|---|
| 演示目标 | 证明购物车之后有订单闭环，并且库存会同步变化 |
| 前置步骤 | 购物车里至少有 1 件商品 |
| 第一步操作 | 在购物车点击 `提交订单` |
| 第二步操作 | 打开顶部订单入口，进入 `我的订单` |
| 第三步操作 | 对订单执行支付、发货、确认收货或退款 |
| 期望现象 | 订单状态变化；下单后库存减少；退款后库存回补；删除订单记录后不应刷新又出现 |
| 重点观察 | 购物车按钮文案不要暴露工程语，比如“同步库存”；售后应在订单里处理，不放在购物车里 |
| 能力点 | Order API、库存扣减/回补、订单状态流转、Android 我的订单页 |
| 现场说法 | 这里不是接真实支付，而是项目路演级的订单闭环模拟，用来说明数据一致性和状态流转。 |

推荐路径：

1. 商品推荐；
2. 加入购物车；
3. 购物车提交订单；
4. 我的订单查看；
5. 支付；
6. 发货；
7. 确认收货；
8. 申请退款；
9. 删除订单记录。

## 9. 拍照找货与图文导购

| 项目 | 内容 |
|---|---|
| 演示目标 | 证明项目有接近真实 App 的拍照找货入口，并且不是只上传图片 |
| 操作步骤 | 点击输入栏相机按钮拍照，或点工具面板选择相册图片 |
| 期望现象 | 上传后输入框短暂显示“正在识别图片...”，随后自动填入类似 `请帮我找类似咖啡、绿色、速溶咖啡的商品` 的可编辑文案；用户确认后用键盘发送 |
| 重点观察 | 发送前用户可以修改预算、品牌、场景等文字；发送后聊天气泡里应显示用户图片，AI 回复商品卡片 |
| 能力点 | Android 拍照/相册上传、upload_id、VLM 图片属性识别、输入框意图回填、图片相似检索、RAG rerank |
| 现场说法 | 这里不是只做了图片按钮，而是让图片先转成可确认的购物意图，再进入同一条 RAG 导购链路。 |

验收路径：

1. 点击输入栏左侧相机按钮；
2. 拍一张商品图并确认；
3. 观察图片预览和“正在识别图片...”提示；
4. 等输入框自动出现识别后的找货文案；
5. 在文案前后补一句预算，例如 `100 元以内`；
6. 用键盘发送；
7. 观察 AI 回复和商品卡片。

如果 VLM 或模型环境暂时不可用，输入框会回填 `请按这张图片找相似商品`，仍可继续演示图片相似检索兜底。如果模拟器相册不好用，可以用 Web Debug 备用演示 upload_id 和 trace。

## 10. 语音输入和语音播报

| 项目 | 内容 |
|---|---|
| 演示目标 | 证明 Android 端具备类似 GPT/豆包的语音输入和 AI 回复播报体验 |
| 操作步骤 | 点击输入框右侧麦克风，说出 `推荐 3500 以内学生记笔记平板` |
| 期望现象 | 系统把语音识别成文字，再按普通文本请求发送；AI 回复结束后，回复下方显示播报和复制两个小图标 |
| 重点观察 | 点击播报后按钮切成停止图标；再次点击可以停止播报；复制按钮能复制当前 AI 文本 |
| 能力点 | Android SpeechRecognizer、语音采集权限、TextToSpeech、播报停止态、文本导购链路复用 |
| 现场说法 | 语音输入和语音播报都复用同一条导购链路，重点是把移动端交互补到接近真实 AI App。 |

如果现场语音组件不可用，直接说明是设备环境问题，切回文本输入，不影响核心 RAG 和 Agent 能力。

## 11. 流式停止与异常兜底

| 项目 | 内容 |
|---|---|
| 演示目标 | 证明前端不是只能等待长回复结束，用户可以主动停止当前生成 |
| 操作步骤 | 输入 `推荐 3500 以内学生记笔记平板，详细说说每款的优缺点`，回复生成中点击输入栏右侧方块停止按钮 |
| 期望现象 | 当前流式请求停止；输入栏恢复可输入；如果已有部分回答，会保留已有文字并追加 `已停止生成。` |
| 重点观察 | 停止后不要继续追加旧回答；不要残留图片预览或发送中状态 |
| 能力点 | Android 流式 Job 取消、SSE 消费停止、临时回复收口、输入栏状态恢复 |
| 现场说法 | 真实 AI 聊天产品需要让用户随时打断长回答，这里验证移动端流式控制。 |

## 12. 反馈闭环

| 项目 | 内容 |
|---|---|
| 演示目标 | 证明赞踩不是装饰，而是可以沉淀成质量评测数据 |
| 操作步骤 | 对一条导购回答点击 `有帮助` 或 `不合适` |
| 期望现象 | 前端提交反馈，后端记录 message_id、rating、comment/reason 等信息 |
| 重点观察 | 反馈应绑定具体回答，不是只在前端变颜色 |
| 能力点 | Feedback API、message_id、反馈日志、反馈闭环评测 |
| 现场说法 | 后续可以把被踩的回答汇总出来，反过来改 Prompt、检索和评测集。 |

## 13. SSE 真流式和异常兜底

| 项目 | 内容 |
|---|---|
| 演示目标 | 证明 Android 不是一次性塞整段文本，而是逐字/分段渲染 |
| 用户输入 | `推荐 3500 以内学生记笔记平板` |
| 期望现象 | 回答逐步出现；如果后端断开，前端显示可理解的失败提示和重试按钮 |
| 重点观察 | 不要现场频繁切网络；如果出现 `SSE_STREAM_ERROR`，先检查后端是否启动 |
| 能力点 | FastAPI SSE、Android 流式消费、统一错误码、重试入口 |
| 现场说法 | 流式输出能让移动端体验更像真实 AI 聊天产品。 |

## 14. 最稳推荐顺序

如果现场时间只有 3-5 分钟，按这条走：

1. `推荐 300 以内通勤鞋`
2. 观察商品卡推荐依据和 trace 中的预算/品类/用途；
3. `要轻便一点的`
4. `如果我更看重耐穿呢`
5. `不要刚才那个品牌`
6. `这两个哪个好`
7. 点商品卡看推荐依据和评价提醒；
8. 点一次 AI 回复下方的播报图标，再点停止；
9. 点一次 `有帮助` 或 `不合适`。

如果现场时间更充足，再补：

1. `推荐 3500 以内学生记笔记平板`
2. `它们两个区别是什么`
3. `100 以内要 Nike 跑鞋`
4. `推荐适合敏感肌的防晒`
5. 语音输入同样的问题；
6. 拍照或相册上传，让 VLM 回填输入框文案后再发送；
7. 在长回答生成中点一次停止按钮。

## 15. 现场讲解口径

路演时尽量围绕这几句话讲：

1. 这个项目不是普通聊天页面，而是后端有 `IntentRouter -> 业务 Agent -> ResponseComposer -> SSE` 的主链路。
2. 商品推荐不是纯大模型编出来的，而是先走 SQLite 结构化过滤、Chroma 召回和 rerank，再由大模型组织成人类导购话术。
3. Android 端已经串起会话、商品卡、详情页、购物车、订单、反馈、图片、语音输入、语音播报和停止生成。
4. 赞踩、评测用例和差评风险不是为了装饰，而是为了让推荐质量能被持续检查和改进。

如果模型现场回答和预期文字不完全一样，不要硬背固定答案。重点看这些稳定现象：

- 是否识别预算、品类、用途和偏好；
- 是否返回商品卡片；
- 是否逐字/分段流式输出；
- 生成中是否可以停止；
- 第二轮是否继承上一轮约束；
- trace 是否有 `guide_quality`，能看到类目 SOP、缺失槽位和证据优先级；
- 对比是否围绕上一轮商品；
- 购物车动作是否实际改变数量和角标；
- 下单后库存是否变化；
- 无严格匹配是否诚实说明；
- 商品卡是否有用户能看懂的推荐依据；
- 拍照后是否能回填可编辑的找货意图；
- 反馈是否实际提交到后端。

## 16. 不建议现场优先展示的内容

- 不优先展示 Web Debug，除非需要看 trace 或排查接口。
- 不优先展示很长的评测报告，除非被问到质量评估。
- 不现场修改 `.env`、重建索引或下载模型，容易受网络和环境影响。
- 不把本地 SQLite、Chroma 索引、模型权重或运行产物当作仓库内容介绍。
- 不讲还没接真实电商平台、真实支付网关的部分，统一说“项目路演级模拟闭环”。
- 对外介绍时统一叫“项目路演”。
